# 예비창업 지원사업 공고 추천 시스템 — 수정 계획서

## 최종 목적

> 전국 또는 서울·경기·인천의 예비창업자·사업자 미보유 창업예정자가 실제 신청할 수 있고, 현재 접수 중이며, 사업화자금·시제품비·R&D·바우처·실증비 등 실질적인 비용지원이 포함된 공고를 사이트 간 중복 없이 하나의 대표 공고로 제공한다.

### 포함 기준
- 예비창업자 신청 가능
- 사업자등록 전 신청 가능
- 전국 또는 서울·경기·인천 대상
- 현재 접수 중
- 사업화자금, R&D, 바우처, 시제품비 등 비용지원 포함
- 교육·멘토링·컨설팅이 부가 프로그램인 경우
- 입주공간과 사업비가 함께 제공되는 경우
- 예비창업자와 창업기업을 동시에 모집하는 경우

### 제외 기준
- 교육만 제공
- 멘토링만 제공
- 컨설팅만 제공
- 투자·IR·데모데이만 제공
- 입주공간만 제공
- 운영기관·수행기관 모집
- 입찰·위원 모집·결과 발표
- 사업자 보유기업만 신청 가능
- 특정 타지역 거주자만 신청 가능
- 접수 마감

| 제목 정규화 | 연도·지역·기관명 제거 | 서로 다른 공고를 동일 공고로 오인할 수 있음 | 연도·지역·차수·재공고 여부 보존 | 필수 |
| 재공고 처리 | `[재공고]` 제거 | 내용·기간이 달라진 재공고를 삭제할 수 있음 | 동일 공고의 신규 버전으로 관리 | 필수 |

| 제외 키워드 | 입주기업·멘토링·컨설팅 등 | 사업비 결합 공고도 제외될 수 있음 | 단독 지원인지 부가 지원인지 분리 | 필수 |

| 적합도 점수 | 참고용 유지 | 구현 복잡도만 높이고 혼란 가능 | 초기에는 비활성화하거나 정렬에만 사용 | 권장 |
| AI 판정 | 애매한 공고만 AI | 방향 적합 | 애매한 사유코드와 호출 상한 필요 | 중요 |
| 성과 검증 | 건수 추정만 있음 | 정확도가 개선됐는지 확인 불가 | 정답 데이터셋과 정확도 KPI 필요 | 필수 |

## 1. 수집 소스 관리 (모듈 A)

### 1-1. Tier 구분 수정

소스 단위로 명확히 구분 (기관명이 아닌 수집 URL/수집기 단위):

| 소스 ID | 사이트 | Tier | 상태 | 비활성 사유 |
|---|---|---:|---|---|
| `bizinfo` | 기업마당 API | 1 | 활성 | - |
| `kstartup` | K-Startup | 1 | 활성 | - |
| `kotra_main` | KOTRA 사업공고 | 2 | 활성 | - |
| `kotra_dup` | KOTRA 재게시 게시판 | 3 | 비활성 | 핵심 게시판과 중복 |

### 1-2. 수집 성공 판정 강화

다음 상황도 장애로 판정:

- HTTP 응답 200이지만 공고 0건
- HTML 구조 변경으로 제목이 모두 빈값
- 20페이지 중 8페이지만 수집
- 수집 건수가 평소 500건에서 갑자기 5건으로 감소
- 기존 공고만 반복되고 최근 공고가 없음

**권장 상태:**

| 상태 | 의미 |
|---|---|
| `OK` | 정상 수집·파싱 완료 |
| `DEGRADED` | 일부 페이지 또는 일부 필드 실패 |
| `FAILING` | 수집 실행 실패 |
| `STALE` | 성공 기록은 있으나 일정 시간 이상 신규 확인 불가 |
| `DISABLED` | 운영자가 비활성화 |
| `UNKNOWN` | 초기 또는 상태 확인 불가 |

**권장 성공 기준:**
```
HTTP/API 성공
+ 예상 페이지 처리 완료
+ 필수 필드 파싱률 충족
+ 비정상적 건수 감소 없음
+ 최신 공고 날짜가 허용 범위 내
```

### 1-3. Tier 2 장애 감지 기준 강화

연속 실패 횟수 + 최종 성공 후 경과시간 병행:

```json
{
  "failure_threshold": 3,
  "expected_interval_minutes": 360,
  "max_staleness_minutes": 1440
}
```

다음 중 하나를 충족하면 경고:
- 연속 실패 횟수 초과
- 마지막 정상 수집 후 허용시간 초과

### 1-4. 상태 저장 구조

최소한 다음 데이터를 분리:

| 데이터 | 목적 |
|---|---|
| 현재 상태 | 알림 및 대시보드 |
| 실행이력 | 원인 분석 |
| 소스 설정 | Tier·주기·임계값 |
| 장애이력 | 알림 중복 방지 |

### 1-5. 알림 폭주 방지

- 정상 → 실패 상태 전환 시 1회 알림
- 실패 지속 중에는 일정 간격으로 재알림
- 동일 오류는 알림 쿨다운 적용
- 정상 복구 시 1회 복구 알림

**알림 필수 정보:**
```
소스명, 상태, 실패 시각, 마지막 성공 시각,
연속 실패 횟수, 수집 건수, 오류 유형, 오류 메시지 요약
```

## 2. 공고 통합·중복 제거 (모듈 B)

### 2-1. 제목 정규화 수정 — 연도·지역·재공고 보존

**삭제하면 안 되는 정보:**
- 사업연도 (2025년 ≠ 2026년)
- 모집 차수 (1차 ≠ 2차)
- 지역 (서울 ≠ 부산)
- 재공고·추가공고·수정공고
- 접수기간

**정규화 대상 (표현 차이만 통일):**
```
2026년 → 2026
모집 공고 → 모집공고
예비 창업자 → 예비창업자
특수문자·중복 공백 제거
```

### 2-2. 재공고·수정공고 버전 관리

```
공고 계열(canonical notice)
 ├─ 최초 공고 version 1
 ├─ 수정공고 version 2
 └─ 마감연장 version 3
```

**발송 정책:**

| 상황 | 처리 |
|---|---|
| 다른 사이트의 완전히 동일한 재게시 | 중복 발송하지 않음 |
| 마감일만 연장 | 변경 알림 발송 가능 |
| 지원대상 변경 | 중요 변경으로 재발송 |
| 첨부파일만 교체 | 변경내용 분석 후 재발송 |
| 오탈자 수정 | 재발송하지 않음 |

### 2-3. 데이터 구조 분리

| 개념 | 설명 |
|---|---|
| 원본 공고 ID (`source_notice_id`) | 각 사이트에서 사용하는 ID |
| 통합 공고 ID (`canonical_notice_id`) | 여러 사이트의 동일 공고를 묶은 ID |
| 발송 이력 (`delivery_history`) | 특정 그룹에 이미 메일로 보냈는지 |

### 2-4. 대표 출처 필드 병합

대표 공고 하나를 선택하는 것이 아니라 출처별 장점을 병합:

```
대표 제목: 주관기관 공식 제목
공식 공고문: 주관기관 URL
신청 링크: K-Startup URL
지원대상: 가장 구조화되고 최신인 값
접수기간: 최신 수정공고 기준
추가 출처: 기업마당, 지역기관
```

### 2-5. 중복 제거 Phase 순서 변경

| 단계 | 내용 | 이유 |
|---|---|---|
| Phase 1 | 공식 공고번호 + 정규화 URL | 정확도가 가장 높음 |
| Phase 2 | 안전한 제목 + 기관 + 연도 + 기간 결합 | 단독 제목 비교 방지 |
| Phase 3 | 공고 버전 및 변경사항 관리 | 수정·연장공고 보호 |
| Phase 4 | 첨부파일 해시 | 정확하지만 다운로드 비용 발생 |
| Phase 5 | 핵심 내용 유사도 | 오탐 검증 필요 |

## 3. 예비창업 공고 매칭 (모듈 C)

### 3-1. 지원내용 판정

**포함할 지원유형:**

| 지원유형 | 예시 |
|---------|------|
| 사업화자금 | 사업화비, 창업지원금 |
| 시제품 제작 | 제품개발비, 시제품 제작비 |
| R&D | 기술개발비, 연구개발비 |
| 바우처 | 제조, 디자인, 마케팅, 수출 바우처 |
| 입주공간 + 사업비 | 공간 + 사업화자금 결합 |
| 판로·실증 | PoC, 테스트베드, 실증비 |
| 지식재산 | 특허·상표 출원비 |
| 마케팅 | 광고비, 콘텐츠 제작비 |
| 해외진출 | 전시회 참가비, 수출지원금 |

**원칙적으로 제외 (단독 제공 시):**
- 교육, 멘토링, 코칭, 상담, 컨설팅, 역량강화, 세미나, 워크숍, 설명회, 네트워킹
- 엔젤투자, VC 투자, 시드투자, 지분투자, 데모데이, IR 피칭

**입주기업 처리 수정:**

| 지원 구성 | 판단 |
|---|---|
| 사무공간만 제공 | 제외 |
| 입주공간 + 사업화자금 | 포함 |
| 입주공간 + 시제품 제작비 | 포함 |
| 입주공간 + 무료 교육 | 원칙적으로 제외 |
| 공간 + 투자연계만 제공 | 제외 |
| 공간 + 실증비 지원 | 포함 |

**`support_types` 변경:**

```
자동 포함 가능:
  지원금, 바우처, R&D, 시제품 제작, 실증·PoC,
  사업비 결합 입주, 비용지원형 판로·마케팅·해외진출

자동 제외:
  교육 단독, 멘토링 단독, 컨설팅 단독, 투자 단독, 입주공간 단독

사람 또는 AI 검토:
  그외, 복합지원, 지원금액 불명확
```

### 3-2. 지원대상 판정 — 신청자와 수혜자 구분

| 역할 | 질문 |
|---|---|
| 신청자 | 누가 신청서를 제출하는가 |
| 수혜자 | 누가 지원을 받는가 |
| 운영자 | 누가 프로그램을 운영하는가 |
| 모집대상 | 이번 공고에서 실제로 모집하는 주체가 누구인가 |

**최종 판단은 신청자 또는 모집대상을 기준으로 함**

**예비창업 인정 표현:**

| 표현 | 판단 |
|------|------|
| 예비창업자 | 인정 |
| 창업예정자 | 인정 |
| 사업자등록을 하지 않은 자 | 인정 |
| 공고일 현재 사업자등록이 없는 자 | 인정 |
| 개인 또는 팀 (단독) | 불충분 — 창업예정·사업자 미등록 조건 결합 필요 |

**예비창업에서 제외해야 하는 대상:**
- 창업기업 대표자만 가능
- 사업자등록증 보유기업만 가능
- 중소기업만 신청 가능
- 대학·기관·협회
- 운영기관·수행기관
- 투자사·액셀러레이터
- 재직자

**예비창업 판정 상태:**

| 상태 | 의미 |
|---|---|
| `ELIGIBLE` | 명확하게 예비창업 신청 가능 |
| `INELIGIBLE` | 명확하게 불가 |
| `CONDITIONAL` | 폐업·업종·대표이력 등 추가 조건 |
| `UNKNOWN` | 확인 불가 |

### 3-3. 제외 키워드 적용 방식 수정

본문 전체 키워드 매칭이 아닌 우선순위로 판단:

```
1순위: 제목과 사업 목적
  - "예비창업자 AI 사업화 지원사업 모집" → 포함
  - "예비창업자 멘토링 프로그램 모집" → 제외
  - "사업화자금 및 멘토링 지원" → 포함

2순위: 주된 지원내용
  - 사업화자금 + 멘토링 → 포함 (자금이 핵심)
  - 교육만 제공 → 제외

3순위: 부가 지원 여부
  - 교육·멘토링·컨설팅이 부가 프로그램이면 제외하지 않음
```

### 3-4. 지원대상 추출 우선순위

```
1순위: 구조화된 지원대상 필드 (target_field)
2순위: 본문의 지원대상 문단
3순위: 첨부 공고문
4순위: 제목 및 요약 (보조)
5순위: AI 판정
```

### 3-5. 자금 포함 공고의 위험 사례

다음은 자금이라는 표현이 있어도 예비창업자가 직접 받는 돈이 아닐 수 있음:
- 운영기관 사업비
- 수행기관 위탁비
- 투자금 유치 교육
- 대출·융자 안내
- 참가비 지원이 아닌 참가비 납부

**핵심 확인:** 예비창업자가 지원대상이며, 예비창업자에게 직접 비용지원이 제공되는가

## 4. AI 판정 범위

### 4-1. AI 전달 사유코드

다음 사유가 하나라도 발생한 경우에만 AI에 전달:

- `TARGET_NOT_FOUND` — 지원대상 문장 불명확
- `APPLICANT_BENEFICIARY_CONFLICT` — 신청자와 수혜자 충돌
- `FINANCIAL_SUPPORT_UNCLEAR` — 비용지원 여부 불명확
- `PRIMARY_SUPPORT_MIXED` — 주된 지원과 부가 지원 혼합
- `REGION_CONFLICT` — 지역 조건 충돌
- `OPERATOR_OR_PARTICIPANT_UNCLEAR` — 운영기관 모집인지 참여자 모집인지 불명확

### 4-2. 추가 통제사항

- 하루 최대 AI 검토 건수
- 동일 공고 결과 캐시
- 공고 내용 변경 시 캐시 무효화
- AI 실패 시 `HUMAN_REVIEW` 상태
- AI 판단 근거 문장 저장
