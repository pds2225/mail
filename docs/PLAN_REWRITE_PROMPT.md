# Mail 모니터 공고 수집·통합·매칭 계획서 전면 수정 요청

아래에 제공하는 기존 「공고 수집 사이트 관리 계획」을 검토하고, 본 프롬프트의 요구사항을 **하나도 누락하지 말고 모두 반영한 통합 실행계획서로 전면 수정하라.**

단순히 의견을 덧붙이거나 일부 문단만 수정하지 말고, 기존 계획서의 오류·충돌·누락을 제거한 **새로운 최종 계획서 전체본**을 작성하라.

이번 작업은 코드 구현이 아니라 **구현 전 최종 계획서 확정 단계**다.  
코드 수정이나 임의 구현은 하지 말고, 실제 개발자가 그대로 TASK로 전환할 수 있을 정도로 구체적인 계획서를 작성하라.

---

# 1. 계획서의 최종 목적

계획서 최상단에 다음 목적을 명확하게 반영하라.

> 전국 또는 서울·경기·인천의 예비창업자, 사업자 미보유 창업예정자가 실제 신청할 수 있고 현재 접수 중이며, 사업화자금·시제품 제작비·R&D·바우처·실증비 등 실질적인 비용지원이 포함된 공고를 최대한 누락 없이 수집한다.  
> 교육·멘토링·컨설팅·투자·입주공간만 제공하는 공고, 운영기관 모집, 행정성 공고, 마감공고는 제외한다.  
> 여러 사이트에 게시된 동일 공고는 하나의 통합 공고로 관리하되, 수정공고·재공고·마감연장 등 중요 변경사항은 별도 버전으로 관리하고 필요 시 다시 안내한다.

계획서의 모든 기능과 우선순위는 위 목적에 맞게 정렬하라.

---

# 2. 전체 구조를 4개 계층으로 분리

기존 계획서는 수집관리, 중복 제거, 예비창업 매칭, 메일 발송이 혼재되어 있다.

최종 계획서는 반드시 다음 4개 계층으로 나누어 작성하라.

## A. 수집 소스 관리 계층

역할:

1. 소스 설정 관리
2. 소스별 수집 실행
3. 재시도
4. 응답 및 데이터 품질 검증
5. 원본 공고 저장
6. 소스 상태 및 실행이력 저장
7. Tier별 장애 알림

## B. 공고 통합·중복 제거 계층

역할:

1. 사이트 내부 중복 제거
2. 공고 필드 정규화
3. 사이트 간 동일 공고 판정
4. 통합 공고 ID 생성
5. 수정·연장·재공고 버전 관리
6. 여러 출처의 정보 병합
7. 대표 원문 및 신청링크 선정

## C. 예비창업 공고 매칭 계층

역할:

1. 행정성·입찰·결과·위원 모집 제외
2. 실제 신청자 및 지원대상 추출
3. 예비창업자 신청 가능 여부 판단
4. 주된 지원과 부가 지원 분리
5. 실질적인 비용지원 여부 판정
6. 신청자 기준 지역 판정
7. 마감 상태 판정
8. 명확한 공고 자동 포함·제외
9. 애매한 공고만 AI 판정

## D. 메일·리포트 발송 계층

역할:

1. 그룹별 발송 이력 확인
2. 동일 공고 중복 발송 차단
3. 중요 변경공고 재발송 여부 판정
4. 대표 원문·신청링크·추가 출처 표시
5. 조건부 공고 표시
6. 발송 결과 저장

각 계층의 입력값, 출력값, 주요 상태값, 오류처리를 계획서에 명시하라.

# 3. 수집 소스 계층 수정사항

## 3-1. 현재 소스 현황 반영

다음 현황을 계획서에 반영하라.

- 활성 소스: 225개
- 비활성 소스: 189개
- Tier 1 핵심 소스:
  - 기업마당 `bizinfo`
  - K-Startup `kstartup`
- Tier 2:
  - NIPA, KIAT, KEIT, KOSME, SBA
  - 지역 테크노파크
  - 경제진흥원
  - 창조경제혁신센터
  - 수출·무역 관련 기관
  - 기타 활성 보조 소스
- Tier 3:
  - JS 렌더링 필요 사이트
  - 접근 차단 사이트
  - 구조 변경 사이트
  - 중복성이 높아 비활성화된 수집 URL

## 3-2. 기관명이 아니라 수집기 단위로 Tier 관리

현재 계획의 KOTRA처럼 동일 기관이 Tier 2와 Tier 3에 동시에 나타나는 충돌을 제거하라.

Tier는 기관명 단위가 아니라 다음 단위로 관리하도록 계획하라.

- `source_id`
- 수집 URL
- API 엔드포인트
- 수집기 또는 어댑터

## 3-3. 소스 성공 여부를 단순 예외 발생 여부로 판정하지 말 것

HTTP 200이나 프로그램 종료 성공만으로 정상 수집으로 판정하면 안 된다.

다음 조건을 함께 검증하도록 계획하라.

- HTTP 또는 API 응답 성공
- 예상 페이지 수 처리 여부
- 필수 필드 파싱률
- 수집 건수의 급격한 감소 여부
- 제목·URL·접수기간 등의 빈값 비율
- 최신 공고 날짜의 신선도
- 일부 섹션만 실패했는지 여부
- K-Startup 공공·민간 영역 각각의 성공 여부
- 페이지 일부만 수집된 부분실패 여부

## 3-4. 소스 상태값

다음 상태를 반영하라.

| 상태 | 의미 |
|---|---|
| `OK` | 정상 수집 및 파싱 완료 |
| `DEGRADED` | 일부 페이지, 일부 필드 또는 일부 영역 실패 |
| `FAILING` | 수집 실행 실패 |
| `STALE` | 마지막 성공 이후 허용시간 초과 또는 신규 공고 신선도 이상 |
| `DISABLED` | 운영자 비활성화 |
| `UNKNOWN` | 초기 상태 또는 판정 불가 |

## 3-5. Tier별 실패 정책 보완

소스별로 다음 값을 설정 가능하게 계획하라.

```json
{
  "expected_interval_minutes": 360,
  "failure_threshold": 3,
  "max_staleness_minutes": 1440,
  "alert_cooldown_minutes": 360
}
```

## 3-6. 알림 폭주 방지

다음 상태 전환 정책을 명시하라.

- `OK → FAILING`: 신규 장애 알림 1회
- `FAILING → FAILING`: 쿨다운 이전에는 재알림 금지
- 장기 장애: 쿨다운 경과 후 재알림
- `FAILING → OK`: 복구 알림 1회
- 복구 후 재실패: 새로운 장애로 처리

## 3-7. 알림 내용

알림에 다음 정보를 포함하도록 계획하라.

- 소스명, 소스 ID, Tier, 상태
- 실패 시각, 마지막 성공 시각, 연속 실패 횟수
- 처리 페이지 수, 수집 건수, 필수 필드 파싱률
- 오류 유형, 오류 메시지 요약, 실행 ID

## 3-8. 상태 저장방식

권장 구조:

```text
source_registry
source_run_history
source_current_health
source_incident_history
```

# 4. 공고 중복 제거 계층 수정사항

## 4-1. 서로 다른 개념을 분리

| 항목 | 의미 |
|---|---|
| `source_notice_id` | 사이트별 원본 공고 ID |
| `canonical_notice_id` | 여러 사이트의 동일 사업을 묶는 통합 공고 ID |
| `delivery_history` | 특정 그룹에 이미 발송했는지 여부 |

## 4-2. 중복 판정 우선순위

1. 공식 공고번호 비교
2. 정규화된 공식 원문 URL 비교
3. 공식 신청 URL 비교
4. 안전한 제목·기관·연도·차수·접수기간 결합 비교
5. 첨부파일 내용 해시
6. 핵심 필드 유사도 비교
7. 게시일 차이는 보조자료로만 사용

## 4-3. 제목 정규화 오류 수정

반드시 보존해야 하는 구분값:

- 사업연도, 모집 차수, 지역, 주관기관
- 재공고·추가공고·수정공고 여부
- 접수기간, 사업명 핵심 고유어

의미 없는 표현 차이만 정규화:

- 중복 공백 제거, 특수문자 통일
- `모집 공고`와 `모집공고` 통일
- `예비 창업자`와 `예비창업자` 통일

## 4-4. 수정·재공고·마감연장 버전 관리

```text
canonical_notice
 ├─ version 1: 최초 공고
 ├─ version 2: 수정공고
 └─ version 3: 마감연장
```

## 4-5. 변경공고 재발송 정책

| 변경사항 | 재발송 |
|---|---|
| 접수기간 연장 | 재발송 또는 변경 알림 |
| 지원대상 변경 | 중요 변경으로 재발송 |
| 지원금액 변경 | 중요 변경으로 재발송 |
| 단순 오탈자 | 재발송하지 않음 |
| 동일 공고 타사이트 재게시 | 재발송하지 않음 |

## 4-6. 대표본 선정이 아니라 필드 병합

```text
대표 제목: 주관기관 공식 제목
공식 공고문: 주관기관 URL
신청 링크: K-Startup URL
지원대상: 최신 구조화 필드
접수기간: 최신 수정공고 기준
추가 출처: 기업마당, 지역기관
```

# 5. 예비창업 공고 매칭 기준 수정사항

## 5-1. 행정성 공고 판정 우선순위

1. 공고의 주된 목적
2. 제목
3. 실제 신청자
4. 주된 지원내용
5. 본문 키워드 보조판정

## 5-2. 명확한 자동 제외 대상

- 입찰, 용역, 구매계약
- 심사위원·평가위원·운영위원 모집
- 직원 채용, 재직자 모집
- 결과 발표, 선정 결과, 보도자료
- 행정고지, 운영기관 모집, 수행기관 모집
- 단순 설명회, 단순 행사 안내

## 5-3. 지원대상 문단 추출 우선순위

1. 구조화된 `target_field`
2. 본문의 지원대상·신청자격 문단
3. 첨부 공고문
4. 제목·본문 요약
5. AI 판정

## 5-4. 신청자와 수혜자 분리

| 역할 | 설명 |
|---|---|
| 신청자 | 실제 신청서를 제출하는 사람 또는 기관 |
| 모집대상 | 이번 공고가 직접 모집하는 대상 |
| 수혜자 | 최종적으로 지원을 받는 대상 |
| 운영자 | 프로그램을 운영하는 기관 |

## 5-5. `개인` 단독 인정 금지

다음과 결합될 때만 인정:

```text
개인 또는 팀
AND
창업예정·사업자 미등록·신규 창업 준비
```

## 5-6. 예비창업 판정 상태

```text
ELIGIBLE
INELIGIBLE
CONDITIONAL
UNKNOWN
```

# 6. 지원내용 판정 수정사항

## 6-1. 포함할 실질 지원

- 사업화자금, 시제품 제작비, R&D 자금, 바우처
- 실증비, PoC 비용, 지식재산 출원비
- 마케팅 비용, 해외전시회 참가비, 수출지원금
- 공간과 사업비 결합지원

## 6-2. 단독 제공 시 제외

- 교육, 멘토링, 코칭, 상담, 컨설팅
- 역량강화, 세미나, 워크숍, 설명회, 네트워킹
- 입주공간만 제공

## 6-3. 투자 단독 제외

- 엔젤투자, VC 투자, 시드투자, 지분투자
- 데모데이, IR 피칭, 투자유치 프로그램

## 6-4. 부가 프로그램 예외 (포함)

- 사업화자금 + 멘토링
- 시제품 제작비 + 교육
- 바우처 + 컨설팅
- 입주공간 + 사업화자금

## 6-5. 입주기업 키워드 일괄 제외 금지

| 구성 | 판단 |
|---|---|
| 입주공간만 제공 | 제외 |
| 입주공간 + 사업화자금 | 포함 |
| 입주공간 + 시제품 제작비 | 포함 |
| 입주공간 + 교육만 제공 | 제외 |

## 6-6. 지원금 수령 주체 확인

> 예비창업자인 신청자가 직접 또는 서비스 형태로 실질적인 비용지원을 받는가

## 6-7. `support_types` 변경

- 자동 포함: 지원금, 바우처, R&D, 시제품 제작, 실증·PoC, 사업비 결합 입주
- 자동 제외: 교육·멘토링·컨설팅·투자·입주공간 단독
- AI/사람 검토: 복합지원, 지원금액 불명확, 그외

# 7. 지역 판정

신청자의 자격조건을 기준으로 판단. 게시기관 소재지가 아님.

| 조건 | 처리 |
|---|---|
| 전국 대상 | 포함 |
| 서울·경기·인천 대상 | 포함 |
| 특정 타지역 거주자만 가능 | 제외 |
| 전국 신청 가능, 선정 후 타지역 이전 필수 | 조건부 포함 |

---

# 8. 마감 판정

상태: `OPEN`, `CLOSED`, `ALWAYS_OPEN`, `UNTIL_BUDGET_EXHAUSTED`, `EXTENDED`, `UNKNOWN`

---

# 9. 적합도 점수

1차 구현에서 비활성화. 포함·제외 기준으로 사용 금지.

---

# 10. AI 판정

기본 모드: `ambiguous_only`

사유코드: `TARGET_NOT_FOUND`, `APPLICANT_BENEFICIARY_CONFLICT`, `FINANCIAL_SUPPORT_UNCLEAR`, `PRIMARY_SUPPORT_MIXED`, `REGION_CONFLICT`, `OPERATOR_OR_PARTICIPANT_UNCLEAR` 등

AI 실패 시 `HUMAN_REVIEW`. 자동 포함·제외 금지.

# 11. 최종 파이프라인

```
① 소스별 공고 수집
② 수집 성공 여부와 데이터 품질 검증
③ 사이트 내부 원본 ID 중복 제거
```

# 17. 금지사항

1. 본문에 멘토링·컨설팅·교육이 있다는 이유로 즉시 제외
2. `개인`만으로 예비창업자 확정
3. 게시기관 소재지로 지역 적격성 판단
4. 사이트 ID만으로 중복 제거
5. 게시일이 다르면 다른 공고로 처리
6. 연도·지역·차수·재공고 표기를 모두 삭제한 제목 비교
7. 수정공고·연장공고를 일반 중복으로 삭제
8. 대표본 하나만 남기고 다른 출처의 최신정보 폐기
9. 투자·교육·멘토링·입주 단독 공고 포함
10. 운영기관 사업비를 예비창업자 지원금으로 오인
11. 적합도 점수로 자동 포함·제외
12. 모든 후보 공고를 기본적으로 AI에 전송
13. AI 실패 시 자동 포함 또는 자동 제외
14. 오류가 없다는 이유만으로 수집 성공 처리
15. 테스트 없이 완료 처리
