> 이 문서는 **야간 자동개발용 실행 프롬프트**다.
> 기준 요구사항은 반드시 `docs/autodev/AI_PRESTARTUP_NOTICE_MASTER_PROMPT.md`를 먼저 읽고 따른다.
> 목적은 계획서만 작성하는 것이 아니라, 저장소를 실제 분석하여 가능한 범위까지 구현·테스트하고, 아침에 사용자가 한 번에 검토·수정할 수 있는 결과를 남기는 것이다.

# 0. 최우선 지시

`docs/autodev/AI_PRESTARTUP_NOTICE_MASTER_PROMPT.md`를 먼저 전체 읽고, 그 문서의 목적·판정기준·금지사항·아키텍처·테스트·KPI를 **상위 요구사항**으로 사용하라.

이번 작업에서는 계획만 작성하고 종료하지 마라.

반드시 다음 순서로 진행하라.

```text
현행 코드 분석
→ 요구사항 대비 GAP 분석
→ 구현계획 확정
→ P0 구현
→ P0 테스트 및 수정
→ P1 구현
→ P1 테스트 및 수정
→ 가능한 P2 구현
→ 전체 회귀테스트
→ 실제 샘플 검증
→ 미해결 항목 정리
→ 아침 검토용 완료보고서 작성
```

사용자 확인을 기다리며 멈추지 마라. 합리적으로 판단 가능한 사항은 기존 코드와 마스터 요구사항을 근거로 스스로 결정하여 계속 진행한다.

단, 다음은 임의로 하지 마라.

- 운영 데이터 대량 삭제
- API 키·토큰·비밀번호 변경 또는 출력
- 외부 서비스 유료 결제
- 운영 메일 대량 발송
- destructive DB reset
- 목적과 무관한 대규모 리팩터링
- 다른 그룹의 정책을 임의 변경

위험하거나 운영에 직접 영향을 줄 수 있는 변경은 코드·마이그레이션·테스트까지 준비하되, 실제 운영 데이터 파괴나 외부 대량 발송은 하지 않는다.

# 1. 이번 야간 작업의 목표

최종적으로 `grp_prestartup_ai`에서 다음 공고만 안정적으로 남도록 구현한다.

> 전국 또는 서울·경기·인천의 예비창업자·사업자 미보유 창업예정자가 실제 신청할 수 있고 현재 접수 중이며, 사업화자금·시제품 제작비·R&D·바우처·실증비 등 실질적인 비용지원이 포함된 공고.

다음은 원칙적으로 제외한다.

- 교육만 제공
- 멘토링만 제공
- 컨설팅만 제공
- 상담·코칭만 제공
- 투자·IR·데모데이만 제공
- 입주공간만 제공
- 운영기관·수행기관·주관기관 모집
- 입찰·용역·위원 모집·채용·결과발표·행정고지
- 사업자등록 보유기업만 신청 가능
- 특정 타지역 대상자만 신청 가능
- 접수 마감

단, 다음은 포함해야 한다.

- 사업화자금 + 멘토링
- 시제품 제작비 + 교육
- 바우처 + 컨설팅
- R&D + 코칭
- PoC 비용 + 상담
- 사업화자금 + IR 교육
- 입주공간 + 사업화자금/시제품비/실증비
- 예비창업자 + 창업기업 동시 모집 공고
- 타지역 기관이 게시했지만 전국 또는 수도권 신청 가능한 공고

# 3. 구현 우선순위

## P0 — 오늘 밤 반드시 최대한 완료

정확도에 직접 영향을 주는 항목이다.

### P0-1. 본문 제외키워드 오판 제거

현재 `멘토링`, `컨설팅`, `교육` 등의 단어가 본문에 존재한다는 이유만으로 정상 공고를 즉시 제외하는 로직이 있다면 제거 또는 수정한다.

판정 우선순위:

```text
공고 주된 목적
→ 제목
→ 실제 신청자/모집대상
→ 주된 지원내용
→ 본문 키워드는 보조판정
```

### P0-2. 실제 신청자·모집대상 추출

단순 본문 전체 키워드가 아니라 다음 순서로 추출한다.

1. 구조화된 `target_field`
2. 지원대상/신청대상/모집대상/참여대상/신청자격/지원자격/신청요건/자격요건 등의 본문 섹션
3. 가능한 경우 첨부 공고문
4. 제목·요약
5. 불명확하면 AI

가능한 범위에서 다음 역할을 구분한다.

- 신청자
- 모집대상
- 수혜자
- 운영자

`예비창업자를 지원할 창업보육 전문기관 모집`은 예비창업 공고로 포함되면 안 된다.

### P0-3. `개인` 단독 예비창업 인정 제거

`개인`, `개인 또는 법인`, `개인사업자`, `개인 신청 가능`만으로 예비창업자로 확정하지 않는다.

다음과 결합되는 경우에만 인정한다.

```text
창업예정
사업자 미등록
신규 창업 준비
선정 후 사업자등록
예비창업팀
```

### P0-4. 주된 지원과 부가 지원 분리

자동 포함 가능:

- 지원금
- 사업화자금
- 바우처
- R&D
- 시제품 제작비
- 실증·PoC 비용
- 비용지원형 마케팅·판로·해외진출
- 사업비가 결합된 입주지원

자동 제외:

- 교육 단독
- 멘토링 단독
- 컨설팅 단독
- 상담·코칭 단독
- 투자 단독
- IR·데모데이 단독
- 입주공간 단독

`사업화자금 + 멘토링`처럼 비용지원이 핵심이고 교육·멘토링이 부가인 경우 반드시 포함한다.

### P0-5. 지원금 수령 주체 판정

본문에 `지원금`, `사업비`라는 단어가 있다고 자동 포함하지 않는다.

다음을 구분한다.

- 예비창업자가 받는 사업화자금 → 포함 가능
- 운영기관 사업비 → 제외
- 수행기관 위탁비 → 제외
- 전체 사업예산 설명 → 포함 근거 아님
- 대출·융자 안내 → 본 그룹의 직접 비용지원으로 간주하지 않음

### P0-6. 지역 판정 수정

게시기관 소재지가 아니라 **신청자 자격조건의 지역**을 기준으로 한다.

- 전국 → 포함
- 지역 제한 없음 → 포함
- 서울·경기·인천 → 포함
- 대구기관 + 전국 대상 → 포함
- 부산 거주자만 → 제외
- 전국 신청 가능 + 선정 후 대구 이전 → `CONDITIONAL`

### P0-7. 마감 상태 판정

다음 상태를 구분한다.

```text
OPEN
CLOSED
ALWAYS_OPEN
UNTIL_BUDGET_EXHAUSTED
EXTENDED
UNKNOWN
```

연장공고가 있으면 최신 마감일을 우선한다.

### P0-8. 적합도 점수의 판정권 제거

기존 `relevance_score`, `llm_check_threshold_band=[40,70]` 등이 최종 포함/제외를 결정하고 있다면 이를 제거하거나 비활성화한다.

기본 권장:

```text
relevance_score_enabled = false
```

점수는 향후 정렬·참고용으로만 사용할 수 있다.

### P0-9. AI는 애매한 공고만

기본값:

```text
llm_review_mode = ambiguous_only
```

AI 검토 사유 예:

- `TARGET_NOT_FOUND`
- `APPLICANT_BENEFICIARY_CONFLICT`
- `FINANCIAL_SUPPORT_UNCLEAR`
- `PRIMARY_SUPPORT_MIXED`
- `REGION_CONFLICT`
- `POST_SELECTION_RELOCATION`
- `DEADLINE_CONFLICT`
- `OPERATOR_OR_PARTICIPANT_UNCLEAR`
- `POSSIBLE_DUPLICATE`
- `ATTACHMENT_ONLY_REQUIREMENT`
- `BUSINESS_HISTORY_CONDITION`
- `MULTIPLE_ELIGIBILITY_RULES`

AI 실패 시 자동 포함 또는 자동 제외하지 말고 `HUMAN_REVIEW`로 보낸다.

### P0-10. 판정 사유 저장

최소한 다음 최종 상태를 추적할 수 있어야 한다.

```text
INCLUDE
EXCLUDE
CONDITIONAL_INCLUDE
HUMAN_REVIEW
DUPLICATE
PROCESSING_ERROR
```

사람이 이해할 수 있는 사유도 함께 남긴다.

# 4. P1 — P0 완료 후 계속 구현

## P1-1. 소스 상태관리 강화

현재 현황:

- 활성 225개
- 비활성 189개
- Tier 1: `bizinfo`, `kstartup`

Tier는 기관명이 아니라 `source_id`/URL/API endpoint/collector 단위로 관리한다.

소스 상태:

```text
OK
DEGRADED
FAILING
STALE
DISABLED
UNKNOWN
```

수집 성공 여부는 단순 HTTP 200이 아니라 다음을 확인한다.

- HTTP/API 성공
- 예상 페이지 처리
- 필수 필드 파싱률
- 수집 건수 급감
- 빈값 비율
- 최신 공고 신선도
- 일부 섹션 실패
- K-Startup 공공/민간 각각의 성공
- 일부 페이지만 실패
- 정상 응답인데 0건인 경우

### Tier 1

- 최초 실패 즉시 알림
- 연속 실패 추적
- 동일 장애 중복 알림 방지
- 쿨다운 후 재알림
- 복구 시 1회 알림

### Tier 2

- 기본 로그
- 연속 실패 임계치 경고
- 마지막 성공 후 최대 허용시간 초과도 경고

소스별 설정 가능하게 한다.

```json
{
  "expected_interval_minutes": 360,
  "failure_threshold": 3,
  "max_staleness_minutes": 1440,
  "alert_cooldown_minutes": 360
}
```

가능하면 단일 `source_health.json`만으로 이력 전체를 관리하지 않는다.

권장 개념:

```text
source_registry
source_run_history
source_current_health
source_incident_history
```

실제 저장소 구조에 맞는 최소 변경으로 구현한다.

## P1-2. 사이트 내부/사이트 간 중복 개념 분리

다음을 분리한다.

```text
source_notice_id      = 사이트별 원본 ID
canonical_notice_id   = 동일 사업 통합 ID
delivery_history      = 그룹별 발송 이력
```

기존 `seen_ids`는 재수집 방지 용도로 유지할 수 있지만 사이트 간 중복·메일 발송이력을 모두 담당하게 하지 않는다.

## P1-3. 중복 판정 우선순위

가능한 범위에서 다음 순서로 구현한다.

1. 공식 공고번호
2. 정규화 공식 URL
3. 공식 신청 URL
4. 안전한 제목 + 기관 + 연도 + 차수 + 접수기간
5. 첨부파일 해시
6. 핵심 내용 유사도
7. 게시일은 보조정보

다른 사이트에 8/17, 8/18 각각 게시되어도 동일 공식 공고번호·사업내용이면 같은 공고로 묶는다.

## P1-4. 안전한 제목 정규화

다음 의미정보는 삭제하지 않는다.

- 연도
- 지역
- 모집차수
- 재공고
- 추가모집
- 수정공고
- 접수기간
- 주관기관

정규화는 표현 차이만 처리한다.

- 중복 공백
- 특수문자
- `모집 공고` / `모집공고`
- `예비 창업자` / `예비창업자`
- 괄호·구분기호
- URL 추적 파라미터

## P1-5. 수정·재공고·마감연장 버전 관리

완전 중복으로 삭제하면 안 되는 변경:

- 접수기간 연장
- 지원대상 변경
- 지원금액 변경
- 제출서류 변경
- 첨부파일 교체
- 수정공고
- 재공고
- 추가 모집
- 1차·2차 모집

개념적으로 다음 구조를 지원한다.

```text
canonical_notice
 ├─ version 1 최초 공고
 ├─ version 2 수정공고
 └─ version 3 마감연장
```

중요 변경은 기존 발송 이력이 있어도 변경알림/재발송 가능하게 한다.

### 재발송 권장

- 마감연장
- 지원대상 변경
- 지원금액 변경
- 신청링크 중요 변경
- 중요 제출서류 변경

### 재발송 금지

- 단순 오탈자
- 다른 사이트의 완전 동일 재게시

## P1-6. 여러 출처 필드 병합

동일 공고에서 한 출처만 남기고 나머지를 버리지 않는다.

권장:

```text
대표 제목 = 주관기관 공식 제목
공식 공고문 = 주관기관 URL
신청링크 = 실제 공식 신청 URL
지원대상 = 최신/구조화된 신뢰 가능한 값
접수기간 = 최신 수정공고 기준
추가출처 = 기업마당, K-Startup, 지역기관 등
```

# 6. 필수 테스트

테스트가 없는 구현은 완료로 처리하지 마라.

최소 다음 테스트를 작성·실행한다.

## 지원대상/지원내용

1. 사업화자금 + 멘토링 → INCLUDE
2. 멘토링 단독 → EXCLUDE
3. 교육 단독 → EXCLUDE
4. 투자 단독 → EXCLUDE
5. 입주공간 단독 → EXCLUDE
6. 입주공간 + 사업화자금 → INCLUDE
7. 운영기관 사업비 → EXCLUDE
8. 예비창업자 또는 창업 3년 이내 → INCLUDE
9. `개인 또는 법인` → 예비창업 자동인정 금지
10. `사업자등록이 없는 개인 또는 팀` → ELIGIBLE
11. `예비창업자를 지원할 운영기관 모집` → EXCLUDE

## 지역

12. 대구기관 + 전국 대상 → INCLUDE
13. 부산 거주자 한정 → EXCLUDE
14. 전국 + 선정 후 대구 이전 → CONDITIONAL_INCLUDE

## 마감

15. 마감일 경과 → EXCLUDE
16. 마감연장 → 최신 마감일 적용
17. 예산 소진 시까지 → OPEN 계열

## 중복

18. 동일 사이트 동일 ID → 중복
19. 타사이트 동일 공고번호 → 동일 canonical notice
20. 8/17 A사이트 + 8/18 B사이트 동일공고 → 1건만 일반 발송
21. 2025/2026 동일 사업명 → 서로 다른 공고
22. 서울/부산 동일 제목 → 별도 공고 가능
23. 1차/2차 모집 → 별도 버전/모집차수 보존
24. 마감연장 → 일반 중복 삭제 금지

## AI/오류

25. AI 정상 JSON
26. AI timeout → HUMAN_REVIEW
27. AI 빈 응답 → HUMAN_REVIEW
28. JSON parse 오류 → HUMAN_REVIEW
29. AI 실패 후 자동 INCLUDE 금지
30. AI 실패 후 자동 EXCLUDE 금지

## 수집 health

31. HTTP 200 + 0건 → 정상으로 단정 금지
32. 일부 페이지만 실패 → DEGRADED
33. 필수 필드 파싱률 급락 → DEGRADED 또는 FAILING
34. Tier 1 신규 장애 → 1회 알림
35. 지속 장애 → 쿨다운 전 중복 알림 금지
36. 복구 → 1회 복구 알림

기존 관련 테스트가 있으면 회귀테스트도 실행한다.

# 7. 구현 중 의사결정 원칙

## 스스로 결정하고 계속 진행할 것

- 기존 코드 스타일에 맞는 파일 위치
- 함수·클래스 이름
- 최소한의 데이터 구조
- 테스트 fixture 위치
- 기존 패턴에 맞는 설정 위치
- 호환성 유지를 위한 adapter/wrapper

## 임의로 확정하지 말 것

- 확인되지 않은 운영 정책
- 운영 데이터 삭제
- 외부 API 신규 결제
- API 키 변경
- 사용자에게 직접 영향을 주는 대량 발송

불확실한 부분은 `HUMAN_REVIEW` 또는 TODO로 남기되, 그 때문에 다른 구현까지 멈추지 마라.

# 8. 자동개발 반복 루프

각 작업은 다음 루프를 따른다.

```text
코드 확인
→ 최소 변경 구현
→ 관련 테스트 실행
→ 실패 원인 분석
→ 수정
→ 재테스트
→ 회귀테스트
→ 완료 여부 기록
```

테스트가 실패하면 실패 상태로 다음 작업을 무조건 덮어쓰지 말고 원인을 분석한다.

단, 한 항목이 외부 의존성 때문에 막혀도 독립적인 다른 항목은 계속 구현한다.

# 9. 아침에 사용자가 한 번에 검토할 수 있도록 반드시 남길 산출물

저장소 내 적절한 위치에 **야간 작업 결과보고서 Markdown**을 생성한다.

# 10. 커밋 정책

가능하면 작업을 논리적인 단위로 커밋한다.

권장 예:

```text
feat: improve prestartup target extraction
feat: classify primary and secondary support types
fix: use applicant eligibility for region matching
feat: add cross-source canonical notice matching
feat: track notice revisions and delivery history
test: add prestartup notice pipeline regression cases
```

하나의 거대한 커밋보다 P0/P1 단위로 구분한다.

테스트 실패 상태를 정상 완료처럼 커밋 메시지에 표현하지 않는다.

# 11. 완료판정

## 완료

- P0 핵심 요구사항 구현
- 관련 테스트 통과
- 기존 주요 회귀테스트 통과
- 심각한 미해결 오류 없음
- 결과보고서 생성

## 조건부 완료

- 핵심 기능은 구현됐으나 외부 의존성/운영정책 때문에 일부 검증 미완료
- 미완료 사항과 후속 방법이 명확함

## 미완료

- 핵심 P0 기능이 동작하지 않음
- 테스트 대량 실패
- 데이터 손상 위험 존재

# 최종 실행 지시

지금부터 저장소를 직접 분석하고 위 작업을 실행하라.

**계획 승인 요청을 위해 멈추지 마라.**

기존 코드와 충돌하지 않는 범위에서 P0 → P1 → P2 순으로 가능한 작업을 계속 진행하고, 각 단계마다 테스트로 검증하라.

외부 의존성 또는 운영 위험 때문에 실행하지 못하는 부분만 명확히 기록하고 다른 독립 작업은 계속 진행하라.

최종적으로 사용자가 아침에 `docs/autodev/AUTODEV_PRESTARTUP_NOTICE_RESULT.md` 하나만 읽어도 다음 사항을 모두 알 수 있어야 한다.

1. 무엇이 실제로 바뀌었는가
2. 무엇이 테스트됐는가
3. 무엇이 실패했는가
4. 무엇을 사용자가 결정해야 하는가
5. 다음에 어떤 수정만 하면 되는가
