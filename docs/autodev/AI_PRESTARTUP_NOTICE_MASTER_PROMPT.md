# Mail 모니터 공고 수집·통합·예비창업 매칭 아키텍처 — AI 전달용 마스터 프롬프트

> 이 문서는 다른 AI에게 **그대로 전달하는 단일 마스터 프롬프트**다.  
> 목적은 기존 `mail` 저장소의 현황을 먼저 확인한 뒤, 공고 수집·소스 상태관리·사이트 간 중복 통합·예비창업 공고 매칭·AI 검토·메일 발송 구조를 **누락 없이 하나의 최종 실행계획서로 재설계**하게 하는 것이다.

---

# 0. 너의 역할과 작업 원칙

너는 `mail` 저장소를 분석하는 시니어 백엔드·데이터 파이프라인 아키텍트다.

이번 단계의 산출물은 **코드 구현 전 최종 실행계획서**다.

다음 원칙을 반드시 지켜라.

1. 저장소의 실제 코드·설정·데이터 구조를 먼저 확인한다.
2. 아래 문서에 적힌 “현재 상태”와 실제 코드가 다르면 실제 코드를 우선하고 차이를 보고한다.
3. 확인하지 않은 파일명·테이블명·함수명·수집주기는 추정하지 않는다. `현행 코드 확인 필요`라고 표시한다.
4. 기존 계획에 잘못된 내용이 있으면 그대로 유지하지 말고 수정 또는 삭제한다.
5. 요구사항을 부록에 추가하는 방식으로 끝내지 말고, 전체 아키텍처와 우선순위에 실제로 반영한다.
6. 결과는 개발자가 추가 해석 없이 TASK로 분해할 수 있을 정도로 구체적으로 작성한다.
7. 이번 단계에서는 임의로 코드를 수정하지 않는다. 단, 계획서에 구현 대상·수정 범위·테스트·마이그레이션·완료조건까지 명시한다.
8. 최종 출력 전 본 문서의 자체 누락검사 체크리스트를 전부 검증한다.

# 1. 최종 사업 목적

최종 시스템의 목적은 다음과 같다.

> **전국 또는 서울·경기·인천의 예비창업자·사업자 미보유 창업예정자가 실제 신청할 수 있고 현재 접수 중이며, 사업화자금·시제품 제작비·R&D·바우처·실증비 등 실질적인 비용지원이 포함된 공고를 최대한 누락 없이 수집한다.**
>
> 교육·멘토링·컨설팅·투자·입주공간만 제공하는 공고, 운영기관·수행기관 모집, 입찰·행정성 공고, 마감공고는 제외한다.
>
> 여러 사이트에 게시된 동일 공고는 하나의 통합 공고로 관리하되, 수정공고·재공고·마감연장·지원대상 변경·지원금액 변경 등 중요한 변경은 별도 버전으로 관리하고 필요한 경우 다시 안내한다.

이 목적을 최상위 기준으로 사용한다.

## 1-1. 포함해야 하는 공고

- 예비창업자 신청 가능
- 사업자등록 전 신청 가능
- 전국 또는 서울·경기·인천 대상
- 현재 접수 중
- 사업화자금, 창업지원금, R&D, 바우처, 시제품 제작비, 실증·PoC 비용 등 실질적 비용지원 포함
- 교육·멘토링·컨설팅이 부가 프로그램으로 결합된 경우
- 입주공간 + 사업화자금/시제품비/실증비 등 비용지원이 결합된 경우
- 예비창업자와 기존 창업기업을 동시에 모집하는 경우

## 1-2. 원칙적으로 제외해야 하는 공고

- 교육만 제공
- 멘토링만 제공
- 컨설팅만 제공
- 상담·코칭만 제공
- 투자·IR·데모데이만 제공
- 입주공간만 제공
- 운영기관·수행기관·주관기관 모집
- 입찰·용역·구매계약
- 심사위원·평가위원·운영위원 모집
- 직원 채용·재직자 대상
- 결과 발표·선정 결과·보도자료·행정고지
- 사업자등록 보유기업만 신청 가능
- 특정 타지역 거주자/창업예정자만 신청 가능
- 접수 마감

  - JS 렌더링 필요 사이트
  - 접근 차단 사이트
  - 구조 변경 사이트
  - 중복성이 높아 비활성화된 수집 URL/어댑터

- 결과 발표, 결과발표, 보도자료, 언론보도
- 기획위원, 심사위원, 운영위원
- 사기피해 예방, 사칭 허위구매, 채용, 재직자

- 지원금/바우처

# 3. 최종 아키텍처는 반드시 4개 계층으로 분리

기존처럼 수집관리·중복제거·매칭·메일 발송을 한 로직에 섞지 않는다.

## A. 수집 소스 관리 계층

역할:

1. 소스 설정 관리
2. 소스별 수집 실행
3. 재시도
4. 응답 및 데이터 품질 검증
5. 원본 공고 저장
6. 소스 상태 저장
7. 실행이력 저장
8. 장애·복구 이력 저장
9. Tier별 알림

## B. 공고 통합·중복 제거 계층

역할:

1. 사이트 내부 원본 ID 중복 제거
2. 공고 필드 정규화
3. 사이트 간 동일 공고 판정
4. `canonical_notice_id` 생성
5. 수정·재공고·마감연장 버전 관리
6. 여러 출처의 정보 병합
7. 공식 원문·신청링크·추가 출처 관리

## C. 예비창업 공고 매칭 계층

역할:

1. 명백한 행정성 공고 제외
2. 실제 신청자·모집대상·수혜자·운영자 추출
3. 예비창업자 신청 가능 여부 판정
4. 주된 지원과 부가 지원 분리
5. 비용지원 여부 및 수령 주체 판정
6. 지역 적격성 판정
7. 마감 상태 판정
8. 명확한 결과 자동 포함·제외
9. 애매한 공고만 AI 검토

## D. 메일·리포트 발송 계층

역할:

1. 그룹별 발송 이력 확인
2. 동일 공고 중복 발송 차단
3. 중요 변경공고 재발송 판단
4. 공식 원문·실제 신청링크 표시
5. 다른 출처 표시
6. 조건부 공고 표시
7. 발송 결과 저장

각 계층별로 **입력값, 출력값, 상태값, 오류처리, 저장 대상**을 계획서에 표로 작성하라.

# 4. 수집 소스 관리 계획

## 4-1. Tier는 기관명이 아니라 수집기 단위로 관리

동일 기관의 서로 다른 게시판이 각각 다른 Tier가 될 수 있다.

다음 단위로 관리한다.

- `source_id`
- 수집 URL
- API endpoint
- collector/adapter

예시:

```json
{
  "id": "kotra_main",
  "name": "KOTRA 사업공고",
  "tier": 2,
  "enabled": true
}
```

```json
{
  "id": "kotra_duplicate_board",
  "name": "KOTRA 재게시 게시판",
  "tier": 3,
  "enabled": false,
  "disabled_reason": "핵심 게시판과 중복"
}
```

계획서에서 KOTRA 등이 Tier 2와 Tier 3에 동시에 적혀 있어도 이를 기관 단위 충돌로 남겨두지 마라.

## 4-2. 수집 성공 여부는 HTTP 성공만으로 판단 금지

다음 조건을 종합 검증한다.

- HTTP/API 응답 성공
- 예상 페이지 수 처리 여부
- 필수 필드 파싱률
- 수집 건수 급감 여부
- 제목·URL·접수기간 등의 빈값 비율
- 최신 공고 날짜 신선도
- 일부 섹션만 실패했는지 여부
- K-Startup 공공/민간 영역 각각의 성공 여부
- 일부 페이지만 수집된 부분 실패 여부
- 정상 응답인데 0건 수집되는 비정상 상황

정상 판정 개념:

```text
HTTP/API 성공
+ 예상 범위 처리 완료
+ 필수 필드 파싱률 기준 충족
+ 비정상 건수 급감 없음
+ 최신 공고 신선도 정상
```

## 4-3. 소스 상태값

```text
OK
DEGRADED
FAILING
STALE
DISABLED
UNKNOWN
```

| 상태 | 의미 |
|---|---|
| `OK` | 정상 수집 및 파싱 완료 |
| `DEGRADED` | 일부 페이지·필드·영역 실패 |
| `FAILING` | 수집 실행 실패 |
| `STALE` | 마지막 성공 이후 허용시간 초과 또는 신규 공고 신선도 이상 |
| `DISABLED` | 운영자 비활성화 |
| `UNKNOWN` | 초기 상태 또는 판정 불가 |

## 4-4. Tier별 실패 정책

### Tier 1

- 최초 실패 즉시 알림
- 연속 실패 횟수 추적
- 동일 장애 지속 중 중복 알림 방지
- 쿨다운 경과 후 장기 장애 재알림
- 정상 복구 시 1회 복구 알림
- 해결에 필요한 오류·수집정보 포함

### Tier 2

- 기본 로그 기록
- 연속 실패 임계값 도달 시 경고
- 마지막 성공 후 허용시간 초과 시 경고
- 단순 `3회 실패`만으로 판단하지 않음

소스별 설정 예:

```json
{
  "expected_interval_minutes": 360,
  "failure_threshold": 3,
  "max_staleness_minutes": 1440,
  "alert_cooldown_minutes": 360
}
```

실제 기본값은 수집주기를 확인한 뒤 결정한다.

## 4-5. 알림 상태 전환

- `OK → FAILING`: 신규 장애 1회 알림
- `DEGRADED → FAILING`: 장애 심화 알림 여부 정의
- `FAILING → FAILING`: 쿨다운 전 재알림 금지
- 장기 `FAILING`: 쿨다운 후 재알림
- `FAILING → OK`: 복구 알림 1회
- `DEGRADED → OK`: 필요 시 복구 로그
- 복구 후 재실패: 새로운 incident

## 4-6. 알림에 포함할 정보

- 소스명
- source ID
- Tier
- 상태
- 실패 시각
- 마지막 성공 시각
- 연속 실패 횟수
- 처리 페이지 수
- 수집 건수
- 필수 필드 파싱률
- 오류 유형
- 오류 메시지 요약
- 실행 ID
- 점검 대상 collector/adapter/file

단순히 `기업마당 수집 실패`만 보내는 계획은 불충분하다.

## 4-7. 상태 저장

단일 `source_health.json`에 현재상태·이력·장애를 모두 넣는 구조를 최종안으로 사용하지 않는다.

권장 논리 구조:

```text
source_registry
source_run_history
source_current_health
source_incident_history
```

계획서에서 다음을 다룬다.

- 현재 상태 저장
- 실행별 이력
- 장애 및 복구 이력
- 동시 실행 안전성
- 서버 재배포 후 상태 보존
- DB 영속성 여부
- 파일 방식이 필요한 경우 원자적 저장
- 임시파일 작성 → 교체
- 손상 복구

# 5. 공고 통합·중복 제거 계획

## 5-1. 세 가지 ID/이력을 반드시 분리

| 항목 | 의미 |
|---|---|
| `source_notice_id` | 사이트별 원본 공고 ID |
| `canonical_notice_id` | 여러 사이트의 동일 사업을 묶는 통합 ID |
| `delivery_history` | 특정 그룹에 이미 발송했는지 여부 |

기존 `seen_ids`는 동일 수집처의 재처리 방지 용도로 유지할 수 있지만 사이트 간 중복과 메일 발송이력을 담당하게 하지 않는다.

## 5-2. 사이트 간 중복 판정 우선순위

다음 우선순위를 기본안으로 사용한다.

1. 공식 공고번호 비교
2. 정규화한 공식 원문 URL 비교
3. 실제 신청 URL 비교
4. 안전한 제목 + 기관 + 연도 + 차수 + 접수기간 결합 비교
5. 첨부파일 내용 해시
6. 핵심 필드 유사도 비교
7. 게시일 차이는 보조정보

## 5-3. 반드시 잡아야 하는 사례

```text
A사이트 게시: 2026-08-17
B사이트 게시: 2026-08-18
공식 공고번호/사업내용은 동일
```

사이트 ID와 게시일이 달라도 하나의 동일 공고로 통합해야 한다.

## 5-4. 제목 정규화에서 의미 있는 정보를 삭제하지 말 것

다음 정보는 보존한다.

- 사업연도
- 지역
- 모집 차수
- 재공고 여부
- 추가모집 여부
- 수정공고 여부
- 접수기간
- 주관기관
- 사업명 핵심 고유어

다음과 같은 표현 차이만 정규화한다.

- 중복 공백
- 특수문자
- 괄호·구분기호
- `모집 공고` ↔ `모집공고`
- `예비 창업자` ↔ `예비창업자`
- URL 추적 파라미터

### 오중복 방지 예시

다음은 서로 다른 공고일 수 있으므로 제목 정규화 과정에서 하나로 만들면 안 된다.

- 2025 예비창업패키지 vs 2026 예비창업패키지
- 서울 공고 vs 부산 공고
- 1차 모집 vs 2차 모집
- 최초 모집 vs 추가 모집
- 최초공고 vs 지원조건이 변경된 재공고

## 5-5. 수정·재공고·연장공고는 버전 관리

다음은 일반 중복으로 삭제하면 안 된다.

- 접수기간 연장
- 지원대상 변경
- 지원금액 변경
- 제출서류 변경
- 신청 URL 변경
- 첨부파일 교체
- 수정공고
- 재공고
- 추가 모집
- 1차/2차 모집

논리 구조:

```text
canonical_notice
 ├─ version 1: 최초 공고
 ├─ version 2: 수정공고
 └─ version 3: 마감연장
```

버전별 관리 항목:

- 변경 일시
- 변경 유형
- 변경 전 값
- 변경 후 값
- 변경 필드
- 중요도
- 재발송 필요 여부
- 원문 출처

## 5-6. 중요 변경 재발송 정책

| 변경 | 기본 처리 |
|---|---|
| 접수기간 연장 | 재발송 또는 변경 알림 |
| 지원대상 변경 | 중요 변경 재발송 |
| 지원금액 변경 | 중요 변경 재발송 |
| 제출서류 변경 | 중요도에 따라 재발송 |
| 신청링크 변경 | 링크 변경 알림 또는 재발송 |
| 단순 오탈자 | 재발송하지 않음 |
| 동일 공고 타사이트 재게시 | 재발송하지 않음 |

## 5-7. 대표본 하나만 선택하는 것이 아니라 필드 병합

여러 출처 중 하나를 버리고 하나만 남기지 않는다.

예:

```text
대표 제목: 주관기관 공식 제목
공식 공고문: 주관기관 URL
신청 링크: 실제 신청 가능한 공식/K-Startup URL
지원대상: 최신·신뢰도 높은 구조화 필드
접수기간: 최신 수정공고 기준
추가 출처: 기업마당, 지역기관 등
```

출처 우선순위 기본안:

1. 직접 발행한 주관기관 공식 사이트
2. 실제 신청이 진행되는 공식 접수 사이트
3. K-Startup
4. 기업마당
5. 지역기관 재게시
6. 기타 민간·재가공 사이트

단, 하위 출처에 더 최신의 공식 수정정보가 확인되는 경우 최신성을 고려한다.

# 7. 지원대상 및 예비창업자 판정

## 7-1. 본문 전체 키워드 검색 중심 방식 폐기

`예비창업자`라는 단어가 본문 어딘가에 있다고 해서 포함하면 안 된다.

잘못된 예:

```text
예비창업자를 지원할 창업보육 전문기관 모집
```

실제 신청자는 기관이므로 예비창업 그룹에서 제외되어야 한다.

## 7-2. 지원대상 추출 우선순위

1. 구조화된 `target_field`
2. 본문의 지원대상/신청자격 문단
3. 첨부 공고문
4. 제목·본문 요약
5. AI 판정

지원대상 문단 라벨 후보:

- 지원대상
- 신청대상
- 모집대상
- 참여대상
- 신청자격
- 지원자격
- 신청요건
- 자격요건
- 신청 가능 대상
- 대상자
- 누가 신청할 수 있나요
- 지원 가능한 자
- 모집 자격

## 7-3. 역할을 분리해서 추출

| 역할 | 의미 |
|---|---|
| 신청자 | 실제 신청서를 제출하는 사람/기관 |
| 모집대상 | 이번 공고가 직접 모집하는 대상 |
| 수혜자 | 최종적으로 지원을 받는 대상 |
| 운영자 | 프로그램을 운영하는 기관 |

최종 매칭은 **신청자와 모집대상**을 최우선으로 판단한다.

## 7-4. 예비창업 인정 의미

다음 의미는 인정 가능하다.

- 예비창업자
- 창업예정자
- 신규 창업 준비자
- 창업을 준비 중인 자
- 사업자등록을 하지 않은 자
- 신청일 현재 사업자등록이 없는 자
- 공고일 현재 사업자 미보유자
- 선정 후 사업자등록 예정자
- 협약 전 사업자등록 예정자
- 개인 또는 팀 단위의 창업 준비자
- 법인설립 전 대표자
- 예비창업팀

고정 키워드뿐 아니라 동의어·띄어쓰기·문장 의미를 고려한다.

## 7-5. `개인` 단독 인정 금지

다음 표현은 예비창업 근거가 아니다.

- 개인
- 개인 또는 법인
- 개인사업자
- 개인회원
- 개인별 상담
- 개인 신청 가능

다음 의미와 결합되는 경우에만 예비창업 판단에 사용한다.

```text
개인 또는 팀
AND
창업예정 / 사업자 미등록 / 신규 창업 준비
```

## 7-6. 명확한 제외 대상

- 사업자등록증 보유기업만 가능
- 기존 법인만 가능
- 중소기업만 신청 가능
- 창업기업 대표자만 가능
- 대학·기관·협회
- 운영기관·수행기관
- 액셀러레이터·투자사
- 재직자
- 컨설턴트·멘토
- 교육기관

단, 아래처럼 예비창업자가 함께 허용되면 포함한다.

```text
예비창업자 또는 창업 3년 이내 기업
```

## 7-7. 기존 사업자·폐업이력 조건은 별도 추출

다음 항목을 구조화해 조건부 판정할 수 있도록 계획한다.

- 기존 사업자 보유 여부
- 동일 업종 사업자 여부
- 이종 업종 사업자 허용 여부
- 폐업 이력
- 폐업 후 경과기간
- 법인 대표이력
- 공동대표 이력
- 선정 전/협약 전 폐업 조건
- 동일 업종 재창업 제한

최종 상태:

```text
ELIGIBLE
INELIGIBLE
CONDITIONAL
UNKNOWN
```

# 9. 지역 판정

## 9-1. 기관 소재지가 아니라 신청자의 자격조건 기준

우선순위:

1. 신청대상/신청자격 문단의 지역조건
2. 거주지 조건

6. 게시기관 소재지

## 9-2. 판정 기준

| 조건 | 처리 |
|---|---|
| 전국 대상 | 포함 |
| 지역 제한 없음 | 포함 |
| 서울·경기·인천 대상 | 포함 |
| 서울·경기·인천에서 창업 예정 | 포함 |
| 특정 타지역 거주자만 가능 | 제외 |
| 특정 타지역 창업예정자만 가능 | 제외 |

### 반드시 통과해야 하는 사례

```text
게시기관: 대구 소재 기관
신청대상: 전국 예비창업자
```

게시기관이 대구라는 이유로 제외하면 실패다.

### 조건부 사례

```text
전국 신청 가능 / 선정 후 대구광역시 내 사업자등록 필수
```

이 경우 `CONDITIONAL`로 표시하고 메일에 조건을 노출한다.

# 11. 적합도 점수 정책

기존 `relevance_score`는 1차 구현에서 최종 포함·제외 기준으로 사용하지 않는다.

## 금지

- 낮은 점수로 자동 제외
- 높은 점수로 자동 승인
- 점수 `40~70` 구간만 AI로 보내기
- 키워드 점수만으로 지원대상 확정

## 권장

1차:

```text
relevance_score_enabled = false
```

- 각 필터별 판정 상태와 이유를 저장
- 자동 포함/자동 제외/조건부/사람검토 상태 사용

단순히 기능 구현 여부만 검증하지 않는다.

1차 가정 KPI:

| KPI | 1차 목표 |
|---|---:|
| 예비창업 공고 정밀도 | 95% 이상 |
| 예비창업 공고 재현율 | 90% 이상 |
| 사이트 간 중복 제거율 | 90% 이상 |
| 잘못된 중복 제거율 | 1% 이하 |
| 사업비+멘토링 오제외 | 0건 |
| 운영기관 모집 오포함 | 0건 |
| `개인` 단독 오포함 | 0건 |
| Tier 1 수집 성공률 | 99% 이상 |
| Tier 1 장애 감지 | 1회 실행주기 이내 |
| AI 전달 비율 | 후보 공고의 20% 이하 |
| AI 실패 후 자동 포함·제외 | 0건 |

위 수치는 **가정 목표치**다. 실제 과거 공고 데이터셋으로 baseline을 측정한 뒤 조정한다.

# 21. 금지사항

최종 계획서에서 다음 구현을 허용하지 않는다.

1. 본문에 `멘토링`, `컨설팅`, `교육`이 있다는 이유만으로 즉시 제외
2. `개인`만으로 예비창업자 확정
3. 게시기관 소재지로 지역 적격성 판단
4. 사이트별 ID만으로 사이트 간 중복 제거
5. 게시일이 다르다는 이유로 다른 공고 처리
6. 연도·지역·차수·재공고 정보를 삭제한 제목 비교
7. 수정공고·재공고·마감연장을 일반 중복으로 삭제
8. 대표본 하나만 남기고 다른 출처의 최신 정보를 폐기
9. 투자·교육·멘토링·입주 단독 공고 포함
10. 운영기관 사업비를 예비창업자가 받는 지원금으로 오인
11. 적합도 점수로 최종 자동 포함·제외
12. 모든 후보를 기본적으로 LLM에 전송
13. LLM 실패 시 자동 포함 또는 자동 제외
14. `source_health.json` 하나만으로 현재상태·실행이력·장애이력을 모두 관리
15. 예외가 발생하지 않았다는 이유만으로 수집 성공 처리
16. `seen_ids`를 사이트 간 중복, 발송이력까지 모두 담당하게 함
17. 테스트 없는 완료 처리
18. 기존 계획의 잘못된 문장을 유지하고 신규 요구사항을 부록으로만 추가

# 23. 계획서 품질 기준

최종 계획서는 다음을 모두 만족해야 한다.

- 단순 요구사항 나열이 아니라 아키텍처에 반영
- 각 판정의 우선순위 명시
- 예외처리 명시
- 상태값 및 reason code 포함
- 데이터 저장·영속성 포함
- 중복과 버전 개념 분리
- source ID / canonical ID / delivery history 분리
- 신청자와 수혜자 분리
- 지원금 수령 주체 확인
- AI 호출 조건 명시
- AI failure-safe 명시
- 테스트 방법 포함
- KPI 포함
- 구현 우선순위 포함
- 기존 설계 오류가 어떻게 변경되는지 비교
- 개발자가 바로 TASK로 전환 가능한 수준
- 확인되지 않은 실제 파일명·테이블명은 임의 확정하지 않음
- 신규 요구사항과 기존 설정이 충돌하면 신규 목적을 우선

# 24. 작성 후 자체 누락검사

최종 출력 전 아래 체크리스트를 전부 검사하라. 누락된 것이 있으면 먼저 계획서를 수정한 후 출력한다.

- [ ] 활성 225개 / 비활성 189개 현황을 실제 코드와 대조했는가
- [ ] Tier 1 `bizinfo`, `kstartup` 실제 구현을 확인했는가
- [ ] Tier를 기관명이 아닌 source/collector 단위로 설계했는가
- [ ] 수집 성공을 HTTP 성공이 아닌 데이터 품질까지 검증하는가
- [ ] `OK/DEGRADED/FAILING/STALE/DISABLED/UNKNOWN` 상태가 있는가
- [ ] Tier 1·2 장애정책과 알림 쿨다운이 있는가
- [ ] 실행이력·현재상태·incident 이력을 분리했는가
- [ ] `seen_ids`, `source_notice_id`, `canonical_notice_id`, 발송이력을 역할별로 분리했는가
- [ ] 8/17 A사이트, 8/18 B사이트 동일공고를 하나로 묶는가
- [ ] 연도·지역·차수·재공고 정보를 제목 정규화에서 보존하는가
- [ ] 수정·재공고·연장공고를 버전 관리하는가
- [ ] 중요 변경 재발송 정책이 있는가
- [ ] 여러 출처의 정보를 병합하는가
- [ ] 본문 `멘토링/컨설팅/교육` 단독 즉시 제외를 제거했는가
- [ ] `입주기업` 단어 단독 제외를 제거하고 공간 단독/사업비 결합을 구분하는가
- [ ] 지원대상 문단을 구조화 필드 → 본문 → 첨부 → 제목/요약 → AI 순으로 추출하는가
- [ ] 신청자/모집대상/수혜자/운영자를 구분하는가
- [ ] `개인` 단독 예비창업 인정을 차단했는가
- [ ] 기존사업자·폐업·대표이력 조건을 조건부 판정할 수 있는가
- [ ] 사업화자금+멘토링 같은 복합공고를 포함하는가
- [ ] 교육·멘토링·컨설팅·투자·입주 단독 공고를 제외하는가
- [ ] 운영기관 사업비를 예비창업자의 지원금으로 오인하지 않는가
- [ ] 지원금의 실제 수령 주체를 확인하는가
- [ ] 게시기관 소재지가 아닌 신청자 지역 기준인가
- [ ] 전국 신청 후 타지역 이전조건을 조건부로 표시하는가
- [ ] 마감연장을 중요 변경으로 처리하는가
- [ ] relevance score를 초기 자동판정 기준으로 사용하지 않는가
- [ ] AI는 `ambiguous_only`가 기본인가
- [ ] AI 호출 사유코드가 정의됐는가
- [ ] AI 실패 시 `HUMAN_REVIEW`인가
- [ ] 실제 공고 100~200건 gold set 검증계획이 있는가
- [ ] 정밀도와 재현율을 모두 KPI로 측정하는가
- [ ] 사이트 간 잘못된 중복 제거율을 측정하는가
- [ ] 소스별 고유공고 기여도와 중복률을 운영지표로 관리하는가
- [ ] P0/P1/P2 구현 우선순위가 있는가
- [ ] 최종 계획서에 요구사항 반영 매핑표가 있는가

# 25. 최종 지시

1. 먼저 저장소의 실제 현황을 조사하라.
2. 기존 설계에서 **유지 / 수정 / 삭제 / 신규 추가** 항목을 내부적으로 구분하라.
3. 사용자에게는 부분 수정안이나 코멘트 목록이 아니라 **모든 요구사항이 반영된 최종 통합 실행계획서 전체본**을 출력하라.
4. 기존 계획과 충돌하는 내용은 그대로 두지 말고 수정하거나 제거하라.
5. 계획서에는 아키텍처, 우선순위, 데이터구조, 상태값, 사유코드, 예외처리, 테스트, KPI, 운영모니터링, 마이그레이션, 완료조건을 모두 포함하라.
6. 마지막에는 본 문서의 체크리스트 각 항목이 최종 계획서 어느 절에 반영됐는지 **요구사항 반영 매핑표**로 증명하라.
7. 확인되지 않은 사실은 추정하지 말고 `현행 코드 확인 필요`로 표시하라.
8. 최종 산출물이 개발자가 바로 구현 TASK로 전환할 수 없는 수준이면 작업을 완료한 것으로 간주하지 마라.
